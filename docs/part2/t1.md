# T1: ActivityPlan to ILP

Implementation: [problem_to_ilp.py](../../transformations/problem_to_ilp.py), issue #4.
Run from the repository root using the existing environment:

```python
from models.instances.tiny_conference import build
from transformations.problem_to_ilp import transform

ilp_model, activity_to_variable = transform(build())
ordered_variables = list(activity_to_variable.values())
```

`transform` accepts a Problem DSL `ObjectModel` containing exactly one ActivityPlan.
It validates structure and invariants before transforming, then validates the generated
Solution DSL model. Invalid input or an unevaluated input check raises `ValueError`
with check details. Invalid or unevaluated generated-output checks raise `RuntimeError`.
The input model is not modified; the output contains new Solution DSL objects.

## Variable order and decoding contract

The returned dictionary maps original activity objects to generated variable objects.
Its insertion order is the case-sensitive Python string ordering of activity DSL names.
Position `i` maps to `y_i`, with `bitWidth=1`. For tiny_conference this is
A/B/C/D → y_0/y_1/y_2/y_3. Input validation already requires unique activity names.

The oracle (#6), T2/search (#7) and Qiskit execution/decoding (#8) must preserve
this order when assigning qubits and decoding bits. Baseline validation (#9) must
interpret results using the same mapping.
Use dictionary order, never BESSER association or object-set iteration order.
A decoded logical bit vector selects each activity whose corresponding bit is 1.
Qiskit measurement-string endianness must be handled at the decoding boundary;
T1 does not interpret measurement strings. This mapping contains live BESSER objects;
it is an in-process API, not a serialization format.

## Rules and assignment references

References use PDF page numbers in `TACS_2627_assignment.pdf`, draft v0.7.

| Rule | Generated model | Reference |
|---|---|---|
| Activity selection | One unsigned one-bit variable per activity | Annex A, class C, pp. 12–13; D3, p. 14 |
| Maximise activity value | Minimise `-sum(value_i * y_i)`, constant 0 | Annex A, class D/D3, pp. 13–14 |
| Conflict | `y_i + y_j - 1 <= 0` | Annex A, D3, p. 14 |
| Mandatory selection | `1 - y_i = 0` | Class C equality-atom syntax, pp. 12–13; event-domain rule |
| Conjunction | No root for zero atoms; the atom for one; AND for two or more | Class C conjunction, pp. 12–13; Solution DSL multiplicities |

Derived conflicts require both half-open interval overlap and a common resource.
Their unordered index pairs are merged with explicit conflicts and sorted before
constructing atoms. Shared resources without overlap, or overlap without shared
resources, add no conflict. Conflicting mandatory activities produce a valid ILP
with no feasible assignments; T1 does not solve or reject infeasible instances.
These event-domain rules are defined in [the concept list](../part1/concepts.md).

The shared validator treats invariants with no context instances as vacuously true,
including inherited context types. This avoids B-OCL's empty-expression error for
models without explicit conflicts or generated linear constraints.

## Verification

```bash
PYTHONDONTWRITEBYTECODE=1 .venv/bin/python -B -m tests.test_problem_dsl
PYTHONDONTWRITEBYTECODE=1 .venv/bin/python -B -m unittest tests.test_solution_dsl tests.test_problem_to_ilp -v
```

T1 tests evaluate the generated expressions for all 16 tiny_conference assignments
and check the unique optimum `{A, C}`, value 7 (objective -7). Additional checks cover
ordering and coefficient alignment, conflict deduplication, interval boundaries,
mandatory selections, infeasibility, constraint-root cardinalities and validation errors.
No quantum execution is involved.
